# Документ AsyncAPI

Сервис, собранный через `#[ruststream::app]`, печатает собственный документ AsyncAPI командой
`cargo run -- asyncapi gen`. Каналы, сообщения и их схемы пишет фреймворк; этот крейт заполняет в
нём половину, относящуюся к AMQP, - за фичей:

```toml
ruststream-lapin = { version = "0.7", features = ["asyncapi"] }
```

Без фичи документ всё равно генерируется, просто в нём нет ничего специфичного для RabbitMQ. С ней
сервис, который читает одну очередь, отвечает через direct reply-to и отправляет
потраченную доставку в очередь для недоставленных, сообщает вот что:

```json
--8<-- "crates/ruststream-lapin/tests/snapshots/asyncapi-amqp.json"
```

## Сервер

`host` и `protocol` говорят, куда подключаются клиенты и на чём они говорят, а `protocolVersion` -
какой именно это AMQP. Различие здесь не украшение: AMQP 1.0 - другой протокол с тем же названием,
другим ключом привязки и другими клиентами, и по адресу хоста их не отличить.

Документ публикуют и передают дальше, поэтому учётные данные из AMQP-адреса в него не попадают.
Брокер, построенный из `amqp://svc:secret@rabbit:5672/prod`, описывает себя как `rabbit:5672` - без
пароля и без виртуального хоста.

## Канал, который читает подписка

Канал подписки - это очередь, и её имя и есть адрес канала. Привязка `amqp` несёт то, что говорит о
ней дескриптор: переживает ли очередь перезапуск, монопольна ли она для одного соединения и
удаляется ли вместе с последним потребителем.

Обменникам, к которым привязана очередь, места здесь нет. Канальная привязка в спецификации - это
либо очередь, либо ключ маршрутизации, а адрес этого канала - очередь.

## Операция приёма

`ack: true` на операции приёма означает, что потребитель подтверждает доставку сам. Этот крейт
всегда так и делает: доставку завершает результат обработчика, а не сам факт её выдачи брокером.

## Канал, в который пишет издатель

Политика публикации описывает канал с другой стороны. `LapinPublish::default().exchange("x")` - это
ключ маршрутизации на обменнике `x`, поэтому привязка сообщает `is: routingKey` и имя обменника. На
обменнике по умолчанию ключ маршрутизации - это имя очереди, поэтому привязка сообщает `is: queue`
и называет эту очередь. Имя берётся из назначения, которое разрешила точка монтирования: из
собственного имени ответа, из объявления `dead_letter(..)`, из имени слота. Политика несёт
настройки публикации и никогда - назначение.

Операция отправки несёт свойства, которые получает каждое сообщение через эту политику:
`deliveryMode` (2 для персистентного значения по умолчанию, 1 для `persistent(false)`), а также
`priority` и `expiration`, если политика их задаёт. Публикация, которая меняет свойство для одного
сообщения, документ не меняет: документ описывает объявление, а не вызов.

Исключение - ответ: собственной операции отправки у него нет, поэтому операционная привязка
политики ответа ни в какой документ не попадает. Канальная попадает.

## Где клиент читает адрес ответа

Обработчик, смонтированный с `DirectReplyTo`, отвечает на каждый запрос туда, куда попросил сам
запрос, поэтому адреса у канала ответа нет. Вместо адреса операция называет заголовок, из которого
он читается, - `$message.header#/reply-to`: это соглашение direct reply-to, записанное как
выражение времени выполнения.

Без этого преобразования ответ уходит на имя, объявленное в точке монтирования, и это имя канал и
сообщает.

## Что остаётся пустым

Двум полям AMQP-привязки из спецификации здесь неоткуда взяться честно. Виртуальный хост живёт в
адресе подключения брокера, которого не видит ни дескриптор, ни политика. Тип сообщения - это имя
типа Rust, которое документ и так сообщает как собственное имя сообщения и которое не узнаёт
функция привязки: ей передают очередь или назначение, а не то, что по ним едет.
