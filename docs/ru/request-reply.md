# Запрос-ответ

RPC поверх RabbitMQ [direct reply-to](https://www.rabbitmq.com/docs/direct-reply-to) - это способ
одному сервису спросить другой через брокер, который у него уже есть, вместо того чтобы заводить
отдельный канал HTTP: сервис заказов проверяет наличие товара в сервисе склада, прежде чем принять
заказ. Обе половины - обычные сервисы; работающая пара -
это [`lapin_rpc_server`](https://github.com/powersemmi/ruststream-lapin/blob/main/crates/ruststream-lapin/examples/lapin_rpc_server.rs)
и [`lapin_rpc_client`](https://github.com/powersemmi/ruststream-lapin/blob/main/crates/ruststream-lapin/examples/lapin_rpc_client.rs).

## Запросчик {#the-requester}

`LapinRequest` - это политика, которая конструирует запросчика `LapinRequester`, а тот реализует
совместимость `RequestReply`. Каждый запрос уходит с `reply-to`, указывающим на псевдоочередь direct
reply-to, и со сгенерированным `correlation-id`, а соотнесённый ответ завершает вызов. Оберните
совместимость небольшим типизированным вызовом:

```rust
--8<-- "crates/ruststream-lapin/examples/lapin_rpc_client.rs:client"
```

Свяжите политику со слотом обработчика в точке монтирования
(`b.include(handler).out(DefaultSlot, Request::default()).build()`),
и обработчик получит живого запросчика параметром `Out`, а значит, вызовет другой сервис посреди
собственного потока сообщений. Граница отказа - это таймаут RPC: содержательный ответ завершает
сообщение, а недоступный сервис просит повторную доставку:

```rust
--8<-- "crates/ruststream-lapin/examples/lapin_rpc_client.rs:handler"
```

## Отвечающая сторона {#the-responder}

Отвечающая сторона - это обычный публикующий обработчик: декодировать запрос, вернуть ответ. `Err`
завершает сообщение без ответа, а механизм восстановления - таймаут у запросчика.

Ответ RPC уходит туда, куда попросил запрос, поэтому его тип не должен объявлять собственного
адресата: `DirectReplyTo` называет адресата для каждой доставки, и точка монтирования отвергает его
над типом ответа, который адресата уже объявил. Клауза `publish("..")` называет адрес для запроса,
пришедшего без заголовка `reply-to`, и именно его сообщает сгенерированный документ AsyncAPI:

```rust
--8<-- "crates/ruststream-lapin/examples/lapin_rpc_server.rs:handler"
```

Отвечающей стороной это делает преобразование. `DirectReplyTo` отправляет каждый ответ обратно на
адрес, о котором попросил запросчик, и повторяет его `correlation-id`; составьте его с издателем
ответов при монтировании:

```rust
--8<-- "crates/ruststream-lapin/examples/lapin_rpc_server.rs:mount"
```

Обработчик остаётся чистой функцией из запроса в ответ, тестируемой внутри процесса, как и любая
другая. Тестируется и пара: `LapinRequest` конструирует запросчика и против
[`LapinTestBroker`](testing.md), который тоже даёт каждому запросу приватный адрес ответа и
`correlation-id`, так что обработчик RPC-клиента и отвечающая сторона работают друг против друга под
`TestApp` с теми же точками монтирования, с которыми они поставляются. Чего внутрипроцессный
транспорт заменить не может - это природы at-most-once, описанной ниже.

## Семантика {#semantics}

- **At-most-once.** Direct reply-to держит состояние ответов в канале запросчика на одном узле
  брокера, и ничего не ставится в долговечную очередь. Оборванный канал теряет ответы в пути, а
  оставшийся без ответа запрос возвращает ошибку по таймауту.
- **По умолчанию временные.** Запросы публикуются с режимом доставки 1, тогда как обычная публикация
  сохраняема. Вы можете пометить их сохраняемыми через `.persistent(true)` на политике.
- **Без инфраструктуры.** Псевдоочередь не объявляется, поэтому единственная настоящая сущность
  здесь - очередь запросов, которую читает отвечающая сторона. Отвечающая сторона на другом стеке
  взаимодействует с этим, пока публикует ответ по полученному `reply-to` и повторяет
  `correlation-id`.
