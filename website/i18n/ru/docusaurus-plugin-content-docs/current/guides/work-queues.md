# Очереди задач

Это руководство делит одну очередь RabbitMQ между воркерами сервиса и сохраняет порядок там, где он важен.

Пример - сервис счетов.
Каждый экземпляр читает одну и ту же очередь `invoices` и формирует документ по каждому взятому счёту.
Вторая очередь пакетами передаёт счета в архив, а третья передаёт их в бухгалтерскую книгу строго в порядке очереди.

## Конкурирующие потребители

Каждый экземпляр сервиса подписывается на одну и ту же очередь.
RabbitMQ отдаёт каждое сообщение одному из них по очереди и никогда двум сразу.
Ещё один запущенный экземпляр - это ещё один потребитель, и очередь разбирается быстрее.
Сообщение, которое экземпляр взял и не подтвердил, возвращается в очередь, когда закрывается его соединение, и его берёт другой экземпляр.

Для этого сервису ничего не нужно: имя очереди в `#[subscriber]` одинаково во всех экземплярах.

[`prefetch`](../components/subscriptions/prefetch.md) ограничивает число неподтверждённых доставок, которые держит подписка, здесь 32.
Пока у потребителя столько неподтверждённых сообщений, RabbitMQ приостанавливает доставку ему.
Поэтому медленный экземпляр перестаёт брать работу, и следующее сообщение уходит экземпляру, у которого есть место.
Без предвыборки RabbitMQ отдаёт очередь потребителям так быстро, как позволяет сеть, и у медленного экземпляра копятся сообщения, которые могли бы взять другие.
Число имеет тип `NonZeroU16`: отсутствие ограничения выражается тем, что значение не задано.
Значение брокера действует для всех подписок, а дескриптор очереди переопределяет его для своей очереди.

Окно предвыборки - свойство сервера, поэтому тест видит его только на работающем RabbitMQ.

`workers(8, by_key)` обрабатывает до восьми счетов одного экземпляра одновременно, в восьми [партициях воркеров](../components/subscriptions/lanes.md).
Биллинговый сервис, который публикует счёт, записывает клиента в заголовок `amqp-partition-key` ([`PARTITION_KEY_HEADER`](api:ruststream_lapin::PARTITION_KEY_HEADER)).
Счета с одинаковым ключом попадают в одну партицию воркеров и обрабатываются друг за другом в том порядке, в каком их получил экземпляр.
Счета разных клиентов обрабатываются параллельно.
Счёт без этого заголовка уходит в следующую по очереди партицию воркеров.
RabbitMQ заголовок не читает: партиции воркеров - соглашение самого сервиса.

Порядок соблюдается внутри одного экземпляра.
Два экземпляра берут каждый свою часть счетов клиента, поэтому их партиции воркеров не упорядочивают счета между экземплярами.
Обработчик читает [`Redelivered`](../components/context/index.md), чтобы записать в журнал, доставлял ли RabbitMQ этот счёт раньше.

Параметр-срез запрашивает [пакет](../components/subscriptions/batches.md), а точка монтирования задаёт его размер через `.batch(nonzero!(64))`.
AMQP доставляет по одному сообщению, поэтому пакет собирается в сервисе.
Пакет закрывается, когда в нём 64 счёта или когда с первого счёта прошло время [`batch_wait`](api:ruststream_lapin::RabbitQueue::batch_wait); по умолчанию это 50 мс.
В пакет попадает только то, что RabbitMQ уже отправил, поэтому очередь архива поднимает собственную предвыборку до 64.
С 32 от брокера ни один пакет не дошёл бы до 64.
Исход обработчика подтверждает каждый счёт пакета.

Бухгалтерской книге нужны все счета в порядке очереди, по всем экземплярам.
Это даёт [единственный активный потребитель](https://www.rabbitmq.com/docs/consumers#single-active-consumer) RabbitMQ: очередь доставляет сообщения одному потребителю, а когда он уходит, его место занимает другой.
У дескриптора нет для этого метода, поэтому [`argument`](../components/subscriptions/arguments.md) передаёт `x-single-active-consumer` в объявление очереди как есть.
Остальные экземпляры остаются подписанными и простаивают, пока не займут его место.

Аргумент - часть объявления очереди.
При `declare_topology(true)` сервис объявляет очередь с ним; очередь, которую создаёт эксплуатация, получает его из её объявления ([Топология](topology.md)).

## Тестирование

Тесты в файле примера публикуют счета с ключом через `with_headers` и проверяют, что счета одного клиента приходят в обработчик по порядку.
RabbitMQ внутри процесса, как и сервер, делит очередь между конкурирующими потребителями и собирает пакеты.
Окно предвыборки и единственный активный потребитель - свойства сервера, поэтому их проверяет [тест на сервере](../components/testing/live.md).
Обвязку разбирает руководство [Тестирование сервиса на RabbitMQ](testing.md).
